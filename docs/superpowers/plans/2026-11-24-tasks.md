# Tasks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A shared team to-do list (Tasks page with categories, a "My tasks" Dashboard card, and an optional "Show tasks" switch on the Schedule), ported from FamillAI without children, XP, repeats, AI or uploaded icons.

**Architecture:** A new backend module `backend/app/tasks/` (schemas, service, routes) beside `app/schedule/`, on a hand-written migration `0007_tasks`; authority rules in `app/auth/policy.py`. A new frontend folder `frontend/src/tasks/` copied from FamillAI's `ui/src/features/tasks/` and rebuilt on KMK's `ui/` pieces, with TanStack Query hooks; a third Dashboard card and task chips on the Schedule.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic (explicit SQL), PostgreSQL, pytest; React 19, React Router 8, TanStack Query 5, i18next, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-24-tasks-design.md` (approved). Reference only, never modified: `/home/user/famillai/ui/src/features/tasks/`, `/home/user/famillai/ui/src/components/{CategoryChips,CategoryDropdown,CategoryManager,SearchBox,FunEmpty}.tsx`, `/home/user/famillai/ui/src/features/home/Dashboard.tsx` (`TasksCard`), `/home/user/famillai/api/src/main/java/com/famillai/services/TaskService.java`.

## Global Constraints

- Every route `Depends(guard())`; GETs use `guard(csrf=False)` like `app/schedule/routes.py` (`reader`). `tests/test_mfa_guard.py` discovers routes from the OpenAPI description, so no edit there is needed, but it must pass.
- Authority in `app/auth/policy.py` only; the frontend `tasks/permissions.ts` mirrors it and only hides controls.
- Audit with `audit.log(db, action, actor_user_id=..., ip=..., details=...)`; details never contain title, description or category name text.
- Error bodies `{"error": "<code>"}`. Codes: `task_not_found` (404), `category_not_found` (404 on its own routes, 422 when referenced from a task), `category_exists` (409), `unknown_person` (422, same code as the schedule), `forbidden` (403), `validation_error` (422, KMK's existing validation handler).
- Limits: title 1-200, description ≤ 2000, category name 1-50, icon ≤ 16 characters (the schedule's `max_length=16`), people ≤ 50, list ≤ 1000 rows.
- Dates are wall-clock dates in `America/Toronto`; front end uses `todayIn(COMPANY_TIME_ZONE)` from `schedule/scheduleDates.ts`.
- Every new UI string in `frontend/src/locales/{en,fr-CA,pt-BR}.json`; task keys start with `task`.
- Migration by hand as SQL; `app/models.py` kept in step; `kmk_app` gets SELECT, INSERT, UPDATE, DELETE.
- Tests never touch the `kmk` database; test first and watch it fail.
- Commit messages end with the Co-Authored-By trailer used in the history. Commit on branch `claude/tasks-familiai-to-kmk-bkqem1`.

## Review Focus

1. **A person on a task whose account is later disabled:** the task still lists, the face is muted, and the task can still be edited without removing them (only newly added people must be active). Test in Task 4 (`test_patch_keeps_disabled_person`).
2. **"Finished today" near midnight:** a task completed at 21:30 Toronto (02:30 UTC next day) counts as today on the Dashboard, not tomorrow. Test in Task 9 (`finishedTodayUsesTorontoDate`).
3. **Clear completed as a plain user:** only deletes the completed tasks that user may delete, and the dialog count matches. Tests in Task 4 (`test_clear_completed_only_deletes_permitted`) and Task 6 (`clearCountOnlyCountsDeletable`).
4. **Completing an already completed task (double tap, two people at once):** idempotent; `completed_at` and `completed_by` are not overwritten. Test in Task 4 (`test_complete_is_idempotent`).
5. **The picked category is deleted while it filters the list:** the list falls back to All instead of showing nothing. Test in Task 8 (`deletedCategoryFallsBackToAll`).

### Task 4: Tasks API

**Files:**
- Modify: `backend/app/tasks/schemas.py`, `service.py`, `routes.py`
- Test: `backend/tests/test_tasks_api.py`

**Interfaces:**
- Produces `TaskIn(BaseModel)`:
  - `title: str` (the `EventIn._title` rules, max 200)
  - `description: str | None` (≤ 2000, stripped, empty → None)
  - `icon: str | None` (max_length 16)
  - `category_id: int | None`
  - `people: list[int]` (each 1..MAX_ID, max 50)
  - `due_date: date | None` (within `FIRST_DAY`..`LAST_DAY` from the schedule schemas)
  - `show_on_dashboard: bool = True`
  - PATCH uses the same model, and the client sends the whole form, as the schedule does.
- Produces `service.task_payload(db, task) -> dict` with keys `id, title, description, icon, category_id, people (sorted ids), status, due_date (ISO or null), completed_at (ISO or null), show_on_dashboard, created_by {id,name}, updated_by {id,name}, created_at, updated_at`. Names come from `schedule.service.display_name`. To avoid N+1 on the list, a batch version `task_payloads(db, tasks) -> list[dict]` loads people and users in two queries.
- Routes:
  - `GET /api/tasks?status=pending|completed|all&person=<id>|none` → `{"tasks": [...]}`
    - default `status=all`
    - order: pending first, then `due_date` ascending with nulls last, then `created_at` descending
    - limit 1000
    - an invalid `person` → 422 `invalid_people`
  - `POST /api/tasks` (201) → `{"task": ...}`
  - `GET /api/tasks/{task_id}` → `{"task": ...}`
  - `PATCH /api/tasks/{task_id}` → `{"task": ...}`
  - `POST /api/tasks/{task_id}/complete` → `{"task": ...}`; `POST /api/tasks/{task_id}/reopen` → `{"task": ...}`
  - `DELETE /api/tasks/{task_id}` (204)
  - `DELETE /api/tasks/completed` → `{"deleted": n}`. Declare it before `/{task_id}`.
- Rules:
  - `category_id` must exist (else 422 `category_not_found`).
  - People are checked like the schedule's `_checked_people`: only newly added people must be `active`, else 422 `unknown_person`. Import and reuse that function rather than copying it.
  - Edit and delete: `policy.check_task`. Complete and reopen: `policy.check_task_status`.
  - Complete on a completed task returns it unchanged. Reopen clears `completed_at` and `completed_by`.
  - `updated_by` and `updated_at = now()` change on every write, including complete and reopen.
- Audit:
  - `task.create {task_id}`
  - `task.update {task_id, fields:[changed names]}`, written only when something changed
  - `task.complete {task_id}` and `task.reopen {task_id}`, only when the status changed
  - `task.delete {task_id}`
  - `task.clear_completed {count}`
